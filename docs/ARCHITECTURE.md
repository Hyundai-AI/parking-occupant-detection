# ExitGuard 시스템 구조 (ARCHITECTURE)

- 작성: 2026-11-26
- 대상: 팀원 전체. 코드를 몰라도 읽을 수 있게 썼습니다.
- 관련: [`DECISIONS.md`](../DECISIONS.md) DEC-005(보드 구성), DEC-007(상태 표시·운전 제어)

> **한 줄 요약**
> 카메라 Pi는 각자 자기 판단만 하고, 판정 Pi(C)는 그 보고를 의심하면서 종합하고, 화면·음성·신호등은 C가 내린 판정을 보여 주기만 한다. **판단할 수 없으면 항상 막는 쪽으로 간다.**

---

## 1. 전체 구성: Pi 4대

```
 [Pi A]   NoIR ─ 내부 인원 모델 ─┐ 유선
 [Pi B]   NoIR ─ 내부 인원 모델 ─┤ 유선
                                 ├──▶ [Pi C] 잔류 인원 판정 ──┬─▶ 터치스크린 (이용자 안내 화면)
 [Pi RGB] RGB  ─ 외부 인원 모델 ─┘ Wi-Fi     Wi-Fi, 카메라 없음 ├─▶ 스피커 (상태별 안내 음성)
                                                              └─▶ 신호등 (ESP32 경유)
```

| 보드 | 카메라 | 하는 일 | 연결 | 설정 파일 |
|---|---|---|---|---|
| Pi A | NoIR | 차량 내부 인원 감지 → C에 보고 | 유선 | `config/node_a.yaml` |
| Pi B | NoIR | 차량 내부 인원 감지 → C에 보고 | 유선 | `config/node_b.yaml` |
| Pi RGB | RGB | 외부 인원(앞좌석 보완) 감지 → C에 보고 | Wi-Fi | `config/node_rgb.yaml` (예정) |
| Pi C | 없음 | 보고 종합 → 최종 판정 → 화면·음성·신호등 | Wi-Fi | `config/hub_c.yaml` |

- **4대 모두 같은 코드를 씁니다.** 각 보드가 무슨 일을 할지는 실행할 때 주는 **설정 파일**로 정하고, 설치는 역할에 필요한 것만 합니다(§7).
  ```
  python -m psafe --config config/node_a.yaml    # Pi A
  python -m psafe --config config/hub_c.yaml     # Pi C
  ```
- 보드끼리는 UDP로 짧은 메시지(JSON)를 주고받습니다. 영상은 보내지 않고 **판단 결과만** 보냅니다.
- 4대는 같은 네트워크에 있고, A·B는 유선, C와 RGB는 Wi-Fi입니다.
- C가 Wi-Fi이므로 **모든 보고가 Wi-Fi 구간을 지납니다.** [실험(EXP-012)](EXPERIMENTS.md)에서 Wi-Fi는 지연 기준을 통과하지 못했습니다(수신 공백 최대 약 400 ms, 무응답 기준 500 ms). 보고가 늦으면 안전한 쪽(판단 불가)으로 가지만, 너무 자주 그러면 빈 차도 막힙니다. 대응은 §9에서 정합니다.

## 2. 지켜야 할 원칙 3가지

1. **막는 건 빠르게, 푸는 건 느리게.**
   사람이 한 번이라도 보이면 즉시 막습니다. "비었다"는 일정 시간 동안 여러 번 확인한 뒤에만 말합니다.
2. **모르면 막는다.**
   카메라 고장, 통신 끊김, 너무 오래된 정보, 선팅으로 안 보임은 모두 "판단 불가(UNKNOWN)"입니다. 판단 불가는 절대 "비었음"이 되지 않습니다.
3. **각자 자기 일만 한다.**
   카메라 Pi는 보고만 하고, C는 판정만 하고, 출력은 표시만 합니다. 예를 들어 화면 코드가 직접 "사람이 있나"를 판단하면 안 됩니다.

## 3. 카메라 Pi(A·B·RGB) 안쪽: 5단계 라인

```
 Source ──▶ Detector ──▶ Health ──▶ FSM ──▶ Link
 (영상 받기)  (YOLO 검출)  (화면 상태)  (내 판단)  (C로 보내기)
```

| 단계 | 하는 일 | 코드 위치 |
|---|---|---|
| Source | 카메라에서 프레임을 가져옴 | `node/sources/` |
| Detector | YOLO로 사람을 찾음 (ONNX, TFLite/Coral) | `node/detectors/` |
| Health | 화면이 너무 어둡거나 밝거나, 멈췄거나, 가려졌는지 검사 | `node/health.py` |
| FSM | 위 결과를 모아 "내 판단" 상태를 정함 | `node/fsm.py` |
| Link | 판단을 C로 보내고, C의 요청을 받음 | `node/link.py` (메시지 형식은 `common/`) |

각 단계는 **부품처럼 갈아 끼울 수 있습니다.** 모델을 바꿔도 Detector만, 카메라를 바꿔도 Source만 바꾸면 됩니다.

### 카메라 Pi의 판단 상태 (FSM)

| 상태 | 뜻 | 언제 |
|---|---|---|
| `INIT` | 시작 중 | 켜진 직후 |
| `OCCUPIED` | 사람 있음 | 사람이 **1프레임만** 보여도 즉시 |
| `VERIFYING` | 사람은 안 보이지만 확인 중 | 사람이 사라진 직후, 장애에서 복구된 직후 |
| `CLEAR` | 내 카메라로는 비었음 | T초 동안, 최소 N프레임 연속으로 사람이 없을 때만 |
| `FAULT` | 내 카메라로는 판단 불가 | 프레임 끊김, 화면 이상, 모델 오류 |

`FAULT`에서 복구되면 바로 `CLEAR`로 가지 않고 `VERIFYING`부터 다시 시작합니다.

## 4. 판정 Pi(C) 안쪽: 의심 많은 판사

```
 보고 받기 ──▶ 신선도 검사 ──▶ 종합 ──▶ 최종 판정 ──▶ 출력들
```

C는 보고를 그대로 믿지 않고 세 가지를 확인합니다.

1. **연락이 끊긴 보드가 있나?** 카메라 Pi는 200 ms마다 보고합니다. **500 ms 동안 소식이 없으면** 그 보드는 무응답으로 처리합니다.
2. **보고가 오래된 건 아닌가?** 근거가 **1초보다 오래됐으면** 믿지 않습니다.
3. **"비었다"고 말하기 전에 한 번 더 확인했나? (CONFIRM)** C가 카메라 Pi들에게 확인 요청을 보내면, 각 카메라 Pi는 **요청을 받은 뒤에 찍은 프레임만으로** 다시 확인해서 답합니다. **3초 안에** 모두 "비었음"이라고 답해야 EMPTY가 됩니다.

> 보드끼리는 시계를 비교하지 않습니다. Pi마다 시계가 조금씩 다르기 때문에, "오래됐는지"는 C가 받은 시각을 기준으로 C 자신의 시계로 판단합니다.

### 최종 판정 4가지

| 판정 | 뜻 | 조건 |
|---|---|---|
| `OCCUPIED` | 사람 있음 | 어느 한 카메라라도 사람을 봄 (합산하지 않음) |
| `UNKNOWN` | 판단 불가 | 어느 하나라도 무응답, 카메라 이상, 근거가 오래됨, 확인 실패 |
| `CHECKING` | 확인 중 | 사람은 안 보이지만 아직 확정 전 |
| `EMPTY` | 비었음 | 모두가 신선한 근거로 비었다고 하고, CONFIRM까지 통과 |

코드 위치: `hub/`(C 실행, 종합), `common/verdict.py`(판정 종류), `node/confirm.py`(카메라 Pi 쪽 재확인 응답).

## 5. 출력: 판정을 보여 주기만 한다

```
 최종 판정 ──┬──▶ 터치스크린
             ├──▶ 스피커
             └──▶ 신호등 (ESP32)
```

세 출력은 모두 같은 판정을 받습니다. 틀(`VerdictOutput`)은 `common/output_api.py`에, 구현체는 `ui/`에 있습니다. 새 출력을 만들 때는 이 틀을 따르기만 하면 되고, 판정 로직은 몰라도 됩니다.

### 판정 → 화면·신호등 표시 (제안, 팀 확정 필요)

판정 이름(코드 내부)과 표시 이름(DEC-007, 이용자에게 보이는 것)은 **서로 다른 층**입니다. 둘 다 쓰고 아래 표로 연결합니다.

| 판정 (코드) | 표시 (DEC-007) | 안내 예시 |
|---|---|---|
| `EMPTY` | IDLE 🟢 | 대기 |
| `CHECKING` | WARNING 🟡 | 확인 중입니다 |
| `OCCUPIED` | WARNING 🟡 → 조건 충족 시 BLOCKED 🔴 | 차량 내부를 확인해 주세요 → 관리자 호출 |
| `UNKNOWN` | BLOCKED 🔴 | 유리창을 내려 주세요 / 장비 점검 필요 |

### 신호등을 ESP32로 거치는 이유
Pi에 바로 연결하면, C 프로그램이 죽었을 때 신호등이 **마지막 색(초록)으로 남을 수 있습니다.** ESP32는 C에게서 **500 ms 동안 소식이 없으면 스스로 운전 불가 표시로 바꿉니다**(워치독).

### 관리자 알림 (HTTP)

위험이 생기면 C가 그 상태를 관리자에게 보냅니다(웹 또는 앱). 이것도 출력 하나(`VerdictOutput`)로 붙이며, 판정 로직은 건드리지 않습니다.

```
 A·B·RGB ──UDP──▶ [Pi C] 판정 ──▶ 터치스크린 · 스피커 · 신호등
                          │
                          └──HTTP──▶ 관리자 (웹 / 앱 알림)
                             위험 발생 시 상태 전송
```

**보드 간 보고는 UDP를 유지하고, 관리자 알림만 HTTP를 씁니다.** 두 통신은 원하는 성질이 반대입니다.

| | 보드 간 보고 (A·B·RGB → C) | 관리자 알림 (C → 관리자) |
|---|---|---|
| 역할 | 안전 판단의 근거 | 위험 상태를 사람에게 알림 |
| 중요한 것 | **늦게 오느니 안 오는 게 낫다** (옛날 "비었음"이 지금 것처럼 들어오면 안 됨) | **늦더라도 반드시 도착해야 한다** |
| 방식 | UDP: 못 받으면 버리고 다음 보고를 기다림 (EXP-012) | HTTP: 받았다는 응답을 확인하고, 실패하면 재전송 |
| 끊기면 | C가 판단 불가(UNKNOWN)로 막음 | 알림만 안 감. 안전 판단에는 영향 없음 |

지켜야 할 점:

1. **알림마다 발생 시각과 상태, 알림 번호를 담습니다.** 재전송 때문에 늦게 도착할 수 있으므로 관리자 화면에 발생 시각을 함께 보여 주고, 같은 알림이 두 번 와도 한 번만 표시합니다.
2. **C가 죽거나 Wi-Fi가 끊기면 알림도 못 보냅니다.** 그래서 C는 평소에도 주기적으로 "살아 있음"을 보내고, 이것이 끊기면 **관리자 쪽에서 "시스템 연결 끊김" 경고**를 띄웁니다(신호등 워치독과 같은 원리).
3. **영상은 보내지 않고 상태만** 보냅니다.
4. 관리자 화면에서 **"비었음 확정"처럼 안전 원칙을 우회하는 조작은 두지 않습니다.** 조작이 필요하면 재검사 요청처럼 막는 쪽·다시 확인하는 쪽만 허용합니다.

## 6. 예시로 흐름 따라가기

**① 뒷좌석에 아이가 잠들어 있고, B 카메라에만 보임**
A: `VERIFYING` / B: `OCCUPIED` → C: 하나라도 봤으므로 `OCCUPIED` → 🟡, 화면 "차량 내부를 확인해 주세요", 음성 안내

**② A 카메라 케이블이 빠짐**
A: 프레임이 안 들어옴 → `FAULT` 보고, 또는 무응답 → C: `UNKNOWN` → 🔴, "장비 점검 필요". B가 "비었음"이라고 해도 A를 알 수 없으므로 **EMPTY가 되지 않음**

**③ 모두 내렸고 차가 비었음**
A·B: 일정 시간 사람이 없음 → `CLEAR` → C: `CHECKING` 상태에서 CONFIRM 요청 → A·B가 새 프레임으로 다시 확인 → 3초 안에 모두 "비었음" → `EMPTY` → 🟢

## 7. 코드 구조와 배포 규칙 (중요)

### 7.1 폴더 = 아키텍처 그림의 상자

레포는 하나이고, `src/psafe/` 아래를 **어느 Pi에서 도는 코드인지**로 나눕니다.

```
src/psafe/
├─ common/    모든 Pi 공통: 메시지 형식, 보드 간 통신(UDP), 시계, 설정, 판정 종류
├─ node/      Pi A·B·RGB: 영상 입력 → YOLO → 화면 상태 검사 → 내 판단(FSM) → C로 보고
├─ hub/       Pi C: 보고 받기 → 신선도 검사 → 종합 → 최종 판정
├─ ui/        Pi C: 출력. 터치스크린 · 음성 · 신호등(ESP32) · 관리자 알림(HTTP)
├─ sim/       개발용: 여러 보드를 PC 한 대에서 시뮬레이션 (Pi에 배포하지 않음)
└─ tools/     개발·측정 도구: 벤치마크, 카메라·통신·Coral 점검
firmware/esp32/   신호등 ESP32 펌웨어
config/           보드별 설정 파일 (node_a.yaml, node_b.yaml, node_rgb.yaml, hub_c.yaml)
scenarios/        자동 시험 시나리오
tests/            자동 테스트 (common · node · hub · ui · 통합)
```

| 폴더 | 들어가는 것 | 도는 곳 |
|---|---|---|
| `common/` | 메시지 형식(Report·Control), UDP 전송, 시계, 설정 읽기, 판정 종류(EMPTY/OCCUPIED/CHECKING/UNKNOWN), 출력 틀(Output·VerdictOutput) | 4대 모두 |
| `node/` | Source, Detector(ONNX, TFLite/Coral), Health, FSM, 재확인(CONFIRM) 응답, 보고 송신 | Pi A·B·RGB |
| `hub/` | 노드 수신 관리, 신선도 검사, 종합(aggregator), 판정 주기 실행 | Pi C |
| `ui/` | 출력 구현체: 판정 콘솔, 신호등(ESP32 프로토콜), 화면, 음성, 관리자 알림 | Pi C |

### 7.2 지켜야 할 규칙

```
 node ──▶ common ◀── hub
             ▲
             └────── ui      (출력 틀 Output·VerdictOutput은 common/output_api.py)
```

1. **`node`와 `hub`·`ui`는 서로 import하지 않습니다.** 양쪽에 필요한 것은 `common`으로 옮깁니다.
2. **메시지 형식은 `common`에만 둡니다.** 보내는 쪽(node)과 받는 쪽(hub)이 반드시 같은 코드를 써야 하기 때문입니다. 복사본을 만들지 않습니다.
3. **`hub`는 `ui`를 import하지 않습니다.** hub는 `common`의 출력 틀(`VerdictOutput`)과 등록부만 알고, 설정 파일에 적힌 이름으로 출력을 만듭니다. 구현체는 `ui`가 등록합니다. 그래서 화면·음성 같은 출력을 추가하거나 바꿔도 판정 코드는 그대로입니다.
4. **`common`을 바꾸면 4대 모두 영향을 받습니다.** 테스트를 통과한 뒤 4대를 같은 커밋으로 한꺼번에 업데이트합니다.

### 7.3 각 Pi가 받는 것: 코드는 통째로, 설치는 역할별로

4대 모두 **같은 레포를 통째로 받고(`git clone`), 설치할 때 자기 역할에 필요한 것만** 설치합니다. 어떤 역할로 돌지는 실행할 때 주는 설정 파일이 정합니다.

| 보드 | 실제로 쓰는 코드 | 설치 | 실행 |
|---|---|---|---|
| Pi A · B · RGB | `common` + `node` | `pip install -e ".[node]"` | `python -m psafe --config config/node_a.yaml` |
| Coral을 꽂은 카메라 Pi | `common` + `node` | `pip install -e ".[node,tflite]" -c requirements/tpu-py312.txt` (Python 3.12) | 위와 같음 (설정에서 Coral 검출기 선택) |
| Pi C | `common` + `hub` + `ui` | `pip install -e ".[hub,ui]"` | `python -m psafe --config config/hub_c.yaml` |
| 개발 PC · CI | 전부 | `pip install -e ".[dev,node,hub,ui]"` | 테스트 · 시뮬레이션 |

설치 그룹별 라이브러리:

| 그룹 | 라이브러리 | 이유 |
|---|---|---|
| 기본 (모두) | numpy, pyyaml | `common`이 씀 |
| `node` | opencv-python-headless, onnxruntime | 영상 처리와 YOLO 추론 |
| `tflite` | tflite-runtime (Python 3.12, numpy<2) | Coral |
| `hub` | (추가 없음) | 판정은 순수 Python |
| `ui` | pyserial (+ 화면·관리자 알림용 라이브러리, 정해지면 추가) | 신호등 ESP32, 출력 |

**Pi C에는 OpenCV나 YOLO 런타임이 설치되지 않습니다.** 판정과 화면만 하므로 가볍게 유지됩니다.

**폴더 일부만 받지(sparse checkout) 않는 이유**
- `common`은 어차피 모든 Pi에 필요합니다.
- 4대가 **같은 커밋**인지 `git rev-parse --short HEAD` 한 줄로 확인할 수 있어야 합니다. 일부만 받으면 이 확인이 어려워집니다.
- 받지 않은 폴더의 코드는 import되지 않으므로 실행에 영향이 없습니다. 차이는 설치되는 라이브러리뿐이고, 그건 설치 그룹으로 나눕니다.

### 7.4 배포 순서

1. 개발 PC에서 테스트 통과(CI 초록불) 후 main에 머지
2. 각 Pi에서 `git pull` 후 `git rev-parse --short HEAD`로 4대가 같은 커밋인지 확인
3. 설치 그룹이 바뀌었으면 위 표의 설치 명령을 다시 실행
4. 서비스 재시작 (자동 실행 설정은 추후 추가)

### 7.5 구조 재구성 진행 상황

사전 MVP(프로토타입)는 기능별 한 패키지(`core/`, `link/`, `safety/`, `sources/`, `detectors/`, `outputs/`)로 만들어 동작과 안전 규칙을 먼저 검증했습니다. 이를 위 구조에 맞게 **계층별로 재구성**하며, 단계마다 해당 테스트를 함께 정리해 CI로 확인합니다.

## 8. 작업 방식

- 변경은 **브랜치 → PR → 머지** 순서로 합니다. 한 PR에는 한 가지 일만 담습니다.
- PR을 올리면 **CI가 자동 테스트와 시뮬레이션 시나리오를 돌립니다** (x86 · ARM64 × Python 3.12 · 3.13). 안전 규칙(예: "사람이 있었는데 비었음이 나간 적 없음")을 깨면 빨간불이 들어옵니다.
- 해야 할 일과 열린 결정은 **Issue**로 관리합니다.
