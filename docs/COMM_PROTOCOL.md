## 1. 기준: 프로토콜 v2 요약 (변경 없음)

| 항목 | v2 |
| --- | --- |
| 구성 | 카메라 Pi(A·B, + RGB) → 판정 Pi C → 출력 Pi D. D가 터치스크린·스피커·신호등(ESP32, 시리얼)을 맡고, C → D는 HTTP(SSE, [UI_SCREEN.md](UI_SCREEN.md)) |
| 전송 | UDP, JSON 1개 = 데이터그램 1개, **최대 512 B**(코드 상한, Report 약 300 B). EXP-012에서 UDP 채택: 끊긴 뒤 옛 메시지가 몰려 오지 않음 |
| 주기 | 노드 → C `Report` 200 ms, C → 노드 `Control` 200 ms. 판단이 안 바뀌어도 계속 보냄 (하트비트 겸용) |
| `Report` | `node`, `boot`, `seq`, `state`(노드 FSM), `safe`, `count`, `reason`, `evidence_age_ms`, `confirm_id`, `confirm`, `echo_seq`, `echo_hold_ms`, `crc` |
| `Control` | `node`, `boot`, `seq`, `confirm_id`, `crc` |
| 무결성 | 마지막 필드 `crc` = 그 앞 바이트 전체의 CRC32. 깨지면 JSON 해석 전에 거부 |
| 중복·재시작 | 같은 `boot`에서 `seq`가 이전 이하이면 무시. `boot`가 바뀌면 재시작, 지나간 `boot`는 무시 |
| 시계 | 보드끼리 시각을 비교하지 않는다. C는 `echo_seq`·`echo_hold_ms`로 왕복 시간을 잰다. **근거 나이 = `evidence_age_ms`(노드가 잰 나이, 추론 시간 포함) + 왕복 시간(전달 시간 상한) + C가 받은 뒤 지난 시간** (`hub/aggregator.py` `_view`). 왕복 시간을 모르면 `<노드>_no_rtt` → 판단 불가 |
| 판정 | 사람(`count > 0`, `state == OCCUPIED`, 재확인 `occupied`) → `OCCUPIED` > `UNKNOWN` > `CHECKING` > `EMPTY`. C 무응답 기준 `hub.node_timeout_ms` 500 → `<노드>_timeout`, 근거 나이 `max_evidence_age_ms` 1000 초과 → `<노드>_stale`, 재확인 3초 초과 → `confirm_timeout` |
| 노드 쪽 무응답 | 카메라 Pi도 C를 따로 감시한다 (`link.node_timeout_ms` 500). C가 무응답이면 재확인 요청을 버리고 `echo_seq`를 비운다 |
| 사람 검출 유실 | 노드는 상태를 200 ms마다 반복하므로, 메시지 하나를 잃어도 `OCCUPIED`는 다음 보고에 그대로 실린다 |

## 2. RGB 노드 규칙

DEC-005: RGB Pi는 **앞좌석(운전석·조수석)과 차량 밖 사람**을 본다. Wi-Fi로 C에 연결된다. ARCHITECTURE §9 1·2번에 대한 규칙이다.

### 2.0 MCU 생존 감시로 보완 (DEC-011, 제안)

RGB Pi는 Wi-Fi라서, 보고가 끊겼을 때 **"Pi가 죽었는지"와 "통신만 끊겼는지"를 C가 구분하지 못한다.** 그래서 RGB Pi 옆에 MCU를 두고 생존을 감시한다.

```
 [Pi RGB] ── 하트비트 (GPIO 또는 시리얼) ──▶ [MCU] ── 이상 통보 ──▶ [Pi C]
 [Pi RGB] ── 판정 보고 Report (UDP, Wi-Fi) ─────────────────────▶ [Pi C]
```

| # | 규칙 (제안) |
| --- | --- |
| M1 | MCU는 RGB Pi의 하트비트가 정해진 시간 동안 끊기면 "RGB 이상"을 C로 보낸다. MCU도 평소에 자기 상태를 주기적으로 보낸다 |
| M2 | C는 MCU 통보를 **막는 쪽으로만** 쓴다. "RGB 이상"을 받으면 RGB를 판단 불가로 처리한다. 반대로 MCU가 "살아 있음"이라고 해도 RGB 보고가 없거나 오래됐으면 그대로 판단 불가다 (MCU 신호로 운전 허가가 나가는 경로를 만들지 않는다) |
| M3 | MCU 자체의 상태 메시지가 끊겨도 C는 이상으로 처리한다 (감시 장치의 고장도 감지) |
| M4 | 화면 안내를 나눈다: MCU가 "RGB 이상" → "앞좌석 카메라 장비 고장", MCU는 정상인데 RGB 보고만 끊김 → "통신 불안정" |
| M5 | MCU → C 메시지는 보드 간 프로토콜 v2의 형식 규칙(UDP + JSON, `boot`·`seq`, CRC)을 따르는 것을 권장한다 (새 메시지 종류 추가, 형식은 메인 코드 담당과 협의) |

- **미확정:** MCU 종류(ESP32 등), RGB Pi와의 연결(GPIO 하트비트 / USB 시리얼), MCU → C 경로(같은 Wi-Fi를 쓰면 Wi-Fi 장애 때 MCU 통보도 같이 끊긴다), 이상 판정 시간, 감시 대상(RGB만 / A·B 포함).
- 아래 G1~G5는 C의 판정 규칙 제안이다. MCU 통보는 G3·G4의 "RGB 무응답·이상" 판단에 근거로 더해진다.

### 2.1 메시지와 설정

- **v2 `Report`를 그대로 쓴다.** 형식 변경 없음, `node: "RGB"`.
- C 설정 `hub.nodes`에 RGB를 추가하고 노드별 `role`·`required`를 둔다 (제안). 아래 주소는 실기 예시다 (각자 다른 Pi라 포트가 같아도 된다. PC 한 대 시험에서는 `config/hub_c.yaml`처럼 포트를 다르게 한다).

```yaml
hub:
  bind: 0.0.0.0:5005
  nodes:
    - { name: A,   address: 192.168.x.a:5006, role: primary }                    # required는 항상 true
    - { name: B,   address: 192.168.x.b:5006, role: primary }
    - { name: RGB, address: 192.168.x.r:5006, role: auxiliary, required: true }  # 기본 true
```

- **설정 검사:** `role: primary`인 노드에 `required: false`를 쓰면 시작할 때 오류로 멈춘다. `required: false`는 `auxiliary`에만 허용한다.

### 2.2 판정 규칙

| # | 규칙 | 이유 |
| --- | --- | --- |
| G1 | RGB가 사람을 보면(`count > 0`, `state == OCCUPIED`, 또는 재확인에 `occupied`) **혼자서도** C 판정은 `OCCUPIED`. 지금 코드의 사람 판정 조건과 같다 | "막는 건 빠르게" 원칙 |
| G2 | **RGB 혼자서는 `EMPTY`를 만들 수 없다.** `EMPTY`는 primary(A·B)가 재확인에서 모두 `empty`라고 답해야 한다 | RGB는 차량 내부(뒷좌석)를 보지 못한다 |
| G3 | `required: true`(**기본값**)이면 RGB를 A·B와 똑같이 취급한다: 무응답·`FAULT`·`INIT`·`stale`·`no_rtt`이면 `UNKNOWN`, 자기 FSM이 `CLEAR`가 아니면 `CHECKING`, 재확인에도 RGB의 `empty`가 필요하다 | RGB가 맡은 앞좌석·차 밖은 A·B의 사각지대일 수 있다 |
| G4 | `required: false`이면, **RGB가 살아 있는 동안에는 G3과 똑같이 막는다** (`OCCUPIED`, 자기 FSM 확인 중 → `CHECKING`). 다만 RGB가 무응답·`FAULT`·`stale`·`no_rtt`일 때, 그리고 재확인에 답하지 못할 때 `EMPTY`를 막지 않는다. 이때 화면에 **"외부 확인 불가"** 를 함께 띄우고 로그에 남긴다 | Wi-Fi 노드라 끊김이 잦을 때 빈 차를 계속 막는 문제(가용성) 대응 |
| G4a | **단, RGB가 마지막으로 보낸 유효 상태가 `CLEAR`가 아니었으면**(사람을 봤거나 확인 중이었는데 끊김) `required: false`여도 `UNKNOWN(RGB_lost_while_<상태>)`으로 막는다. RGB가 돌아와 `CLEAR`를 다시 보내야 풀린다 | 사람을 본 직후 끊기면, 끊김을 핑계로 `EMPTY`가 되는 구멍을 막는다 (비대칭 판단 원칙) |
| G5 | `required: false`로 바꾸려면 **두 가지 근거가 모두 필요하다**: ① 사각지대 시험(E-22)에서 A·B만으로 앞좌석까지 덮는다는 기록 ② 차량 밖 사람 확인을 다른 수단(입고실의 기존 광전센서·매트 등, 요구사항 "범위"의 제외 항목)이 맡는다는 확인. 근거 없이 바꾸지 않는다 | 가용성 때문에 안전을 몰래 낮추지 않기 위해 |

- **구현 메모:** G3은 지금 `hub/aggregator.py`에 노드 하나를 추가하는 것만으로 동작한다 (모든 노드를 같게 취급). G4·G4a는 `required`에 따른 분기와 "노드별 마지막 유효 상태" 기억을 새로 넣어야 한다.
- 화면 표시: 노드별 상태를 따로 보여 준다 (예: "앞좌석 카메라: 연결 끊김"). 합계 인원을 보여 주지 않는 기존 원칙과 같다.

## 3. Wi-Fi 운용 규칙 (제안)

> 이 절은 **제안**이다. 적용 여부는 메인 코드·장비 담당과 협의해 정한다.

C와 RGB가 Wi-Fi라서 **모든 보고가 Wi-Fi 구간을 지난다** (DEC-005). 지금까지의 측정:

| 출처 | 측정 방식 | 결과 |
| --- | --- | --- |
| EXP-012 ② | **판정 메시지 패턴**: 300 B를 5 Hz로 띄엄띄엄 송신, 300초. **Wi-Fi 절전 켜짐**, 11/25 16시 | UDP 왕복 p50 13.7 ms, p99 71.2 ms, 최대 150 ms, 수신 공백 최대 326 ms |
| `comm_data` 4.2·4.4 | **연속 왕복**: 응답을 받자마자 다음 요청 (16 B~8 KB), 3회. 절전 설정 기록 없음, 11/26 15시 | UDP 16 B 중앙값 2.76 ms·p99 9.95 ms. 꼬리는 1 KB부터 커짐(`tcp` 1 KB p99 평균 54.1 ms, 최대 147 ms), 중앙값은 8 KB에서 급증. 회차마다 값이 흔들림 |
| `comm_data` 4.1·4.2 | 유선 직결(eth0) | iperf3 941 Mbps·손실 0, UDP 16 B 중앙값 0.154 ms, 24개 조건 p99 0.16~2.27 ms. **Wi-Fi보다 5.1~37.0배 빠름** |

두 Wi-Fi 측정은 **송신 패턴이 다르다.** 연속 왕복은 무선 카드가 쉴 틈이 없어 절전의 영향이 작게 나올 수 있고(추정), 판정 메시지처럼 띄엄띄엄 보내면 절전으로 잠들었다 깨는 지연이 드러난다. **기준값은 판정 메시지 패턴으로, 절전을 끈 상태에서 다시 재야 한다** (M1).

### 3.1 규칙

| # | 규칙 |
| --- | --- |
| W1 | **모든 Pi의 Wi-Fi 절전을 끈다.** 재부팅해도 유지되게 NetworkManager 연결 설정으로 한다: `sudo nmcli connection modify <Wi-Fi 연결 이름> 802-11-wireless.powersave 2` 후 **`sudo reboot`**. (연결을 내렸다 올리면 Wi-Fi로 붙은 SSH가 끊기므로 재부팅이 안전하다.) 확인: `iw dev wlan0 get power_save` → `Power save: off` |
| W2 | **판정 메시지는 v2 상한(512 B) 안에서, 가능한 한 지금 크기(약 300 B)를 유지한다.** `comm_data`에서 Wi-Fi 꼬리 지연은 1 KB부터 커졌다. 필드를 추가할 때는 크기를 같이 확인한다 |
| W3 | **무응답 기준은 "연속으로 몇 개까지 잃어도 되는가"로 정한다.** `node_timeout_ms` = `k` × 200 + `J`. `k` = 허용할 연속 유실 개수(제안 2), `J` = 지터 여유 = M1에서 잰 (수신 간격 p99.9 − 200 ms)를 50 ms 단위로 올림. 예: `k`=2, `J`=150 → 550 ms. **C(`hub.node_timeout_ms`)와 모든 노드(`link.node_timeout_ms`)를 같은 값으로 맞춘다.** 노드 쪽만 짧으면 노드가 먼저 C를 무응답으로 보고 재확인을 버려 `no_rtt`·`confirm_timeout`이 늘어난다 |
| W3a | **근거 나이 한도 점검:** `max_evidence_age_ms`(1000)는 정상 상태에서 생기는 최대 근거 나이보다 커야 한다. 정상 최대 = 노드가 보낼 때의 근거 나이 + 왕복 p99(`R`) + C가 받은 뒤 다음 판정까지 최대 200 ms. 노드 쪽 근거 나이는 보통 `max_frame_age_ms`(500) 안이지만, 하트비트가 같은 판단을 다시 보낼 때는 `max_decision_age_ms`(600) + 하트비트 주기까지 늘어 **최악 약 800 ms**다 (팀 EXPERIMENTS E-10). 계산: 보통 500 + 75 + 200 = 775, **최악 800 + 75 + 200 = 1075 > 1000.** 즉 지금 값으로도 Wi-Fi p99 지연이 겹치면 정상 상태에서 가끔 `*_stale`이 날 수 있다 → M1에서 `*_stale` 발생 빈도를 함께 보고, 잦으면 `R`을 줄이거나(W1·W5) 조원과 한도를 다시 정한다. **W3으로 `node_timeout_ms`를 늘려도 이 계산은 그대로**다 (끊긴 동안은 근거 나이가 아니라 무응답으로 먼저 막힌다) |
| W3b | **요구사항과 숫자 맞추기:** 요구사항 R2의 허용 나이(제안 1.5초)와 코드의 `max_evidence_age_ms`(1.0초)가 다르다. 코드 값이 더 엄격하므로 요구사항 문서를 코드 값으로 고치거나, 확정 시 둘을 같이 바꾼다 (조원 합의) |
| W4 | **가용성 기록:** C 로그에서 `*_timeout`·`*_no_rtt`·`*_stale`·`confirm_timeout` 발생 횟수를 시간당으로 센다. 목표는 요구사항 "안정성": **30분 연속 동작 중 R2(감시 이상) 오발생 0건.** 넘으면 W3 값을 다시 보거나 W5로 간다. 기준을 늘려서 가용성을 얻을 때는 안전 쪽 영향(끊김 감지가 늦어짐)을 함께 기록한다 |
| W5 | **유선 우선:** 고정 설치(교실·모형)에서는 C를 유선으로 연결하는 것을 우선 검토한다. `comm_data`에서 유선은 p99가 2.3 ms 이하였다. C가 유선이면 A·B 보고는 Wi-Fi 구간을 지나지 않는다 |
| W6 | **같은 망의 다른 트래픽과 분리:** 진단용 영상(MQTT, 수십 KB/장)은 판정 메시지와 같은 Wi-Fi를 쓰면 지연을 키울 수 있다. 판정 시험 중에는 영상 전송을 끄거나, 영상은 유선 직결(`10.10.10.x`)로만 보낸다. M3에서 영향을 잰다 |

## 4. 외부 실험(휴대폰 핫스팟) 주소 절차

> **현장 확인 후 확정.** 실제 현장(기계식 주차장)을 가 본 뒤 전원·공간·전파 상황에 맞춰 고친다. 아래는 그 전까지의 초안이다.

외부 실험은 휴대폰 핫스팟으로 하고, **그때 IP를 다시 배정해 설정 파일에 적는다** (고정 IP 방식 유지). 핫스팟에서는 A·B도 무선이 되므로, 3절 측정을 핫스팟에서도 한 번 해야 한다.

### 4.1 학교에서 미리 할 일 (출발 전)
1. **핫스팟 Wi-Fi를 모든 Pi에 미리 등록한다.** 현장에서는 Pi에 접속할 방법이 없으므로 반드시 출발 전에 한다:
   `sudo nmcli connection add type wifi con-name hotspot ssid "<핫스팟 이름>" wifi-sec.key-mgmt wpa-psk wifi-sec.psk "<비밀번호>" connection.autoconnect-priority 10` (비밀번호는 각자 입력. 우선순위를 학교 Wi-Fi보다 높게 해 핫스팟이 켜져 있으면 그쪽에 붙게 한다)
2. 이 연결에도 W1(절전 끔)을 적용한다.
3. **같은 휴대폰으로 학교에서 리허설한다:** Pi 5대 + 노트북을 핫스팟에 붙이고 ① 6대 동시 접속이 되는지(기종마다 최대 접속 수가 다름) ② Pi끼리 `ping`이 되는지 ③ 실제 `psafe` C·노드를 띄워 보고가 오가는지(UDP) 확인한다. **일부 핫스팟은 기기끼리 통신을 막는다(격리).** 막히면 그 휴대폰으로는 진행할 수 없으므로 다른 기종을 쓴다.
4. 모든 설정 파일의 `bind`를 `0.0.0.0:<포트>`로 둔다 (PC 시험용 `127.0.0.1`이면 다른 Pi의 메시지를 받지 못한다).

### 4.2 현장에서
1. 모든 Pi와 노트북을 핫스팟에 붙인다.
2. **IP 찾기:** 휴대폰 "연결된 기기" 목록에 IP가 보이면 그대로 쓴다. 보이지 않으면(일부 기종은 이름만 보임) 노트북에서 `ping <호스트 이름>.local` 또는 노트북의 `arp -a`로 찾고, SSH로 접속해 `hostname`으로 어느 Pi인지 확인한다.
3. C의 `hub.nodes` 주소와 A·B·RGB의 `link.hub` 주소를 새 IP로 고치고 실행한다. 바꾼 IP와 시각을 실험 기록에 남긴다.
4. **시작 확인:** C 로그에서 노드마다 처음 한 번 `restart`(첫 부팅으로 받아들임) 뒤 `ok`가 계속 늘고, `*_timeout`·`*_no_rtt`가 0인지 확인한다. 노드 로그에서도 C가 살아 있는지 확인한다(양방향).
5. 핫스팟을 껐다 켜면 IP가 바뀔 수 있다. 그러면 2~4를 다시 한다. IP가 바뀌면 C는 그 노드를 무응답으로 보고 막는 쪽으로 간다 (안전하지만 실험이 멈춤).

## 5. 메시지 위조 방지 (제안, E-26)

**문제:** 같은 망의 다른 장치가 `node: "A"`로 `Report`를 보내면 C가 믿는다. 반대로 가짜 `Control`을 노드에 보내면 재확인을 방해할 수 있다. CRC는 우연한 깨짐만 막는다. 교실 Wi-Fi·핫스팟은 다른 조·다른 기기와 같은 망이다.

| 안 | 내용 | 막는 것 | 비용 |
| --- | --- | --- | --- |
| S1 | **보낸 주소 확인 (양쪽):** C는 `Report`의 `node` 이름별로 설정에 적힌 IP와 보낸 IP가 같을 때만 받는다 (A의 IP로 `node: "B"`를 보내도 거부). 노드도 `Control`이 설정의 C IP에서 왔을 때만 받는다. 맞지 않으면 `unknown_addr`로 세고 무시 | **설정 실수와 다른 조 프로그램이 섞이는 것** | 형식 변경 없음. 수신 함수가 이미 보낸 주소를 함께 돌려준다 (`transport.recv()` → `(데이터, (IP, 포트))`) |
| S3 | **공유 키 HMAC:** CRC 자리에 HMAC-SHA256(미리 나눠 가진 키) 일부를 싣는다 | 키를 모르는 장치의 위조 | 형식 변경(v3), 키 배포·보관 |

- **제안 순서:** 지금은 S1만 (코드 몇 줄, 형식 그대로). S3는 v3를 만들 일이 생길 때 검토한다.
- **S1의 한계를 문서에 그대로 적는다:** IP는 흉내 낼 수 있으므로 S1은 보안 장치가 아니라 **혼선 방지**다. 포트는 비교하지 않는다(OS가 바꿀 수 있음). IP가 바뀌면(4.2 5번) 그 노드가 막히는데, 이것은 안전한 쪽 실패다.
- r3에 있던 S2(시스템 구분 값 `sys`)는 S1으로 대부분 막히고 형식 변경 비용이 커서 뺐다.
